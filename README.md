  thread 3 / team size 4
串行区（Join 后）：再次只有主线程执行。
[通过] parallel 并行域实际创建了 4 个线程。
```

### 问题

1. 主线程进入 `parallel` 前、并行域内、离开并行域后分别处于什么状态？请用 Fork-Join 模型解释。

答：进入 `parallel` 前，只有主线程在串行执行，此时并行域尚未创建；遇到 `parallel` 指令时发生 Fork，运行时按 `OMP_NUM_THREADS` 派生出线程团队（本实验为 4 个线程，主线程编号 0 也是团队成员之一），团队共同执行并行域内的代码块；离开并行域时发生 Join，除主线程外的其他线程被回收，程序又回到只有主线程执行的串行区。

2. 本次运行实际创建了多少线程？线程编号的范围是什么？

答：实际创建了 4 个线程，线程编号范围是 0～3。

3. 程序为什么每次都按 0、1、2、3 的顺序输出线程信息？请指出负责输出的代码位于并行域内还是 Join 后的串行区。这个输出顺序能否证明线程按编号顺序执行？

答：负责打印的 `for` 循环位于并行域外、Join 之后的串行区。并行域内每个线程只把自己的 team size 写进 `team_size_by_thread[线程号]` 这个与编号一一对应的数组位置；Join 之后主线程再按数组下标 0→3 从小到大遍历打印，所以输出永远显示 0、1、2、3。这个顺序是打印代码强加的顺序，不能证明并行域内线程按编号顺序执行——并行域内各线程的实际执行顺序和交错是不确定的。

## Q02：为什么按行并行不需要给 `y` 加锁（3 分）

### 实验记录

  thread 2: 1024 行

```

### 问题

1. `parallel for` 如何把外层行循环分给多个线程？一次执行中，一行会由几个线程负责？

答：`parallel for` 是工作共享结构，运行时把外层行循环的迭代空间按调度策略切分成若干份，分发给团队中的各线程；每个迭代（即每一行）只被分配给一个线程执行，所以一次执行中一行只由一个线程负责。

2. 为什么不同线程写 `y[row]` 时通常不需要 `atomic` 或 `critical`？

答：因为每个迭代只对应一个不同的 `row`，不同线程写的是 `y` 数组里互不重叠的下标位置，不存在多个线程同时写同一个 `y[row]` 的情况，因此没有数据竞争，也就不需要同步。

3. `matrix.row_ptr`、`matrix.col_idx`、`matrix.values`、`x` 和 `y` 中，哪些对象由线程共同读取，哪些位置由线程独立写入？

答：`matrix.row_ptr`、`matrix.col_idx`、`matrix.values` 和 `x` 被所有线程共同读取（只读）；`y[row]`（以及辅助观察用的 `row_owner[row]`）由各线程对各自负责的行独立写入，不同线程写不同下标。

4. 如果改为让多个线程共同计算同一行，结论会发生什么变化？

答：若多个线程一起算同一行，它们会同时对同一个 `y[row]` 累加，从而产生数据竞争；此时就必须用 `reduction`、`atomic` 或 `critical` 等机制安全合并部分结果。“一行只被一个线程写”这个按行划分的前提就不成立了。

## Q03：哪些变量应为 `shared` 或 `private`（3 分）

### 修复记录

简述初始代码中 `shared_sum` 导致的两个问题，以及你的修改：

答：初始代码有两个问题。其一是逻辑错误：`shared_sum` 声明在行循环外，且每行开始前没有清零，导致从第 2 行起累加值不断累积到上一行的结果里。其二是数据竞争：`shared_sum` 被声明为 shared，多个线程无同步地同时读写同一个标量。修复方法是把累加器移到行循环体内，声明成每行的局部变量 `float sum = 0.0F;`，这样每进入一行都重新初始化为 0，且每个线程/每次迭代各有一份、天然私有；同时从 `shared(...)` 列表中删掉 `shared_sum`，保留 `shared(matrix, x, y)`。

### 数据属性分析

| 对象或变量 | 数据属性/作用域 | 原因 |
| --- | --- | --- |
| `matrix` | shared | 只读的公共输入，所有线程都要读 row_ptr/col_idx/values |
| `x` | shared | 只读的输入向量，所有线程都要读 x[col] |
| `y` | shared | 输出数组，但各线程写的是互不重叠的 y[row] |
| `row` | private（循环变量，隐含） | 工作共享循环的循环变量自动私有 |
| `index` | private（循环体内局部） | 每行内层循环的循环变量，各迭代独立 |
| 每行累加器 | private（每行局部变量） | 每行从 0 开始，线程间、行间互不影响 |

### 问题

1. 为什么仅仅把共享累加器写进 `private(...)` 不一定是最清晰、最安全的修复？

答：`private(shared_sum)` 只会给每个线程一个未初始化的私有副本，并不会自动在每行开始时清零；只要累加器仍放在行循环外，即使消除了竞争，逻辑上仍是“所有行共用一个不断累积的数”，结果依旧错误。正确做法是把累加器的声明位置移到行循环体内，让它随迭代的生命周期自动初始化、自动销毁，而不是靠 `private` 子句去补救一个作用域错误。

2. `default(none)` 会迫使程序员做什么？它能否自动消除所有数据竞争？

答：`default(none)` 强制程序员显式声明并行域内引用的每一个外部变量的数据属性（shared/private 等），漏掉任何一个都会在编译时报错，从而帮助发现遗漏。但它只是让“谁共享、谁私有”显式化，并不能自动消除数据竞争——两个线程仍可被显式声明为 shared 并同时写同一个变量，此时竞争依然存在，仍需靠划分写入范围或同步手段来解决。

### 问题

1. 对 uniform 矩阵，三种调度的工作分配有什么特点？

答：uniform 每行长度相同，因此分到相近的行数就意味着分到相近的 nnz，三种调度的 nnz 都接近均分（约 26 万）。static 一次性连续划分、几乎完全平均（每线程 16384 行）；dynamic 和 guided 按 chunk 动态领取，行数有小幅波动，但 nnz 仍非常接近。

2. 对 skewed 矩阵，为什么“每个线程分到相近的行数”仍可能不均衡？

答：skewed 把 61 个非零元的长行集中在前四分之一，其余行只有 1 个非零元，所以“行数相近”不等于“工作量相近”。static 把连续的前 16384 行（恰好全是长行）分给 thread 0，其余线程只分到 1-nnz 的短行，导致 thread 0 承担 999424 nnz、其他线程只有 16384 nnz，严重不均衡。

3. 哪种调度在你的机器上更快？请同时考虑负载均衡和调度开销，不能只根据一次耗时下结论。

答：uniform 上 static 最快（0.112ms）、guided 次之、dynamic 最慢（0.154ms），因为 uniform 本就均衡，dynamic 的动态领取只增加开销而没有均衡收益；skewed 上 dynamic 最快（0.186ms），因为它按 chunk 动态分配，克服了长行集中带来的不均衡，而 static（0.558ms）和 guided（0.554ms）都让 thread 0 独占长行而成为瓶颈——guided 的初始 chunk 较大、恰好覆盖前四分之一的长行，所以表现接近 static。可见没有绝对最快的调度：工作均匀时用开销低的 static，工作不均匀时用 dynamic 换均衡。

4. chunk 大小改变时，你预计分配粒度和运行时开销怎样变化？

答：chunk 越小，分配粒度越细、负载越容易均衡，但线程领取工作的次数越多、调度开销越大；chunk 越大，领取次数减少、开销降低，但一次领取的工作块变大，遇到长行集中的矩阵时更容易重新出现不均衡。对 uniform 这类均匀矩阵，大 chunk（甚至 static）即可；对 skewed，适中的小 chunk 才能在开销与均衡之间取得平衡。

## Q05：什么时候需要同步和 `reduction`（3 分）

### 实验数据

| 方法 | 结果是否正确 | 时间/ms | 共享更新如何处理 |
| --- | --- | ---: | --- |
| 错误共享更新 | 错误 | 0.334 | 多线程直接累加同一个 sum，无同步 |
| `atomic` | 正确 | 16.184 | 每次累加用 atomic 原子更新 |
| `critical` | 正确 | 21.589 | 用 critical 临界区串行化每次累加 |
| `reduction` | 正确 | 0.057 | 每线程私有副本，最后统一归约合并 |

### 问题

1. 错误共享更新为什么存在数据竞争？某次输出恰好正确能否证明程序正确？

答：多个线程同时对同一个共享变量 `sum` 执行“读—加—写”，这个复合操作不是原子的，线程之间会互相覆盖中间结果，所以存在数据竞争。某次输出恰好正确只能说明这次的交错没有暴露覆盖，是偶然结果，不能证明程序正确——数据竞争的结果依赖线程调度时序，不可复现、不可依赖。

2. `atomic`、`critical` 和 `reduction` 在同步粒度与并行性上有什么区别？

答：`atomic` 只把单条变量的更新变成原子操作，粒度最细、串行化范围最小；`critical` 把整段代码标记为临界区，粒度最粗，同一时刻只允许一个线程进入；`reduction` 让每个线程在私有副本上独立累加、最后统一合并，各线程的累加过程完全并行，只在归约合并点同步一次，并行性最好。

3. 工作共享循环末尾的隐式 barrier 保证了什么？如果后续代码不依赖全部循环结果，`nowait` 可能带来什么收益和风险？

答：隐式 barrier 保证所有线程都完成各自迭代（对 reduction 而言即归约合并完成）之后，后续代码才继续执行，因此循环结束后可以安全读取最终归约结果。若后续代码不依赖全部循环结果，用 `nowait` 可以让先完成的线程跳过等待、立即去做后续工作，减少等待时间、提高并行性；风险是此时不能读取尚未完成的归约结果或尚未写完的共享数据，否则会读到部分结果。

4. 为什么按行基线通常不需要对 `y` 使用 `reduction`？如果多个线程共同计算一行，结论会怎样变化？

答：按行基线中每行只由一个线程负责，`y[row]` 各写各的下标、互不重叠，本就没有共享累加，自然不需要 reduction。若多个线程共同计算同一行，就会同时向同一个 `y[row]` 累加而产生竞争，此时必须用 reduction 或 atomic/critical 把各线程的部分和合并后一次写入。

S_p=\frac{T_1}{T_p}

E_p=\frac{S_p}{p}

### 问题

1. 小矩阵和大矩阵的加速趋势有何不同？

答：小矩阵从 1 到 4 线程几乎不再加速（S 从 1.0 到约 1.28 就饱和），效率掉到 0.319；大矩阵加速更明显，4 线程达到 3.32 倍、效率 0.830。说明问题规模越大，并行收益越能摊薄固定开销。

2. 线程创建、工作分配、隐式同步等固定开销为何会影响小问题？

答：并行化本身要付出创建/回收线程团队、划分循环迭代、末尾隐式 barrier 等待等固定开销，这些开销与问题规模无关。小矩阵计算量极小、串行时间本来就短，固定开销占比很大，甚至可能抵消乃至超过并行省下的时间，所以小问题加速不明显甚至变慢。

3. 即使负载完全均衡，为什么内存访问和程序中的串行部分仍会限制加速比？请结合 Amdahl 定律说明。

答：Amdahl 定律给出 S_p = 1 / ((1-f) + f/p)，其中 f 是并行部分比例，串行部分 1-f 给加速比设了上限：p→∞ 时 S_p 最多到 1/(1-f)，无法无限加速。此外 SpMV 是访存密集型计算，多个线程要共享内存带宽、竞争缓存，内存带宽成为新的瓶颈，即使负载均衡也无法线性扩展。这些共同解释了为什么 4 线程效率只有约 0.83 而不是 1。

若程序中可并行部分比例为 $f$，Amdahl 定律给出的理论加速比为：

$$
S_p=\frac{1}{(1-f)+\frac{f}{p}}
$$

## Q07：最终四线程 OpenMP SpMV（4 分）

### 最终方案

1. 描述你的并行方式、调度策略和 chunk 选择。

答：采用按行划分的 `parallel for`，用 `default(none) shared(matrix, x, y)` 显式声明数据属性；调度采用 `schedule(dynamic, 64)`，即以 64 行为一个 chunk 动态分配给线程。选择 dynamic 是因为公开与隐藏矩阵的行长度分布未知，动态调度能在长行集中的情况下把负载摊平；chunk 取 64 在“领取次数带来的调度开销”与“负载均衡”之间取得平衡——chunk 太小调度开销增大，太大又在长行集中的矩阵上退回到静态分块的不均衡。

2. 说明你使用了哪些实验一范围内的普通 C++ 循环优化，以及为什么它们仍符合本实验规则。

答：在内层循环中用局部变量 `begin`/`end` 缓存 `row_ptr[row]` 和 `row_ptr[row+1]`，避免重复访问行指针数组；用 `const auto position = static_cast<size_t>(index)` 统一计算下标，减少重复类型转换。这些都只是普通、可移植的 C++ 循环写法，交由编译器在 `-O2 -march=native` 下自行优化，不涉及手写 SIMD 内建、内联汇编或外部计算库，因此符合本实验规则。

3. 说明你的实现如何在 1、2、4 线程下保持正确，并说明是否改变了浮点加法顺序。

答：并行化只作用于外层行循环，每个 `row` 迭代仍由单一线程完成，`y[row]` 的写入位置互不重叠，因此无论运行时团队是 1、2 还是 4 个线程，每行结果都与串行一致（1 线程时即退化后的串行行为）。浮点加法顺序没有改变：每行内仍按非零元的原始顺序从头到尾累加，行与行之间本就互不影响，所以数值结果与串行基线相同。

4. 如果最终方案不是按行划分，请说明工作如何分配，以及同一输出元素的部分结果如何安全合并。

答：本方案是按行划分，不涉及多个线程共同计算同一行，因此同一输出元素不会产生需要合并的部分结果，无需额外同步。

### 结果分析

1. 为什么学生 1 线程版本可能比固定串行基线慢？

答：学生 1 线程版本仍要经过 OpenMP 并行域的创建/回收、循环工作共享划分等运行时开销，而固定串行基线没有这些开销；在只有 1 个线程时这些开销无法靠并行摊薄，所以学生 1 线程略慢于串行基线（如 banded 2.3555ms vs 2.3491ms）。

2. 你的并行划分和调度对 uniform、随机和行长度不均匀矩阵分别有什么影响？

答：banded（uniform）各行 nnz 相同，动态调度只带来少量领取开销，加速比仍达 2.405；random 行长度随机但整体较均匀，动态调度均衡尚可（2.585）；skewed 行长度严重不均匀，dynamic 能显著摊平长行集中的负载，因此在三个合成矩阵中加速比最高（2.845）；cage11 是真实稀疏矩阵、规模较小，但并行充分，加速比达 3.000、效率 0.750，是四者中最好的。

3. 哪类矩阵从四线程获得的收益最小？请从每行工作量、调度开销和内存访问角度分析。

答：均匀带状矩阵 banded 从四线程获得的收益最小（S4=2.405、E4=0.601 均为最低）。原因：它的每行工作量完全一致、访存连续规整、缓存局部性最好，串行基线已经把内存带宽利用得很充分，四线程并行很快撞上内存带宽瓶颈，多出的线程只能争抢带宽；同时 dynamic 调度在均匀负载下只增加领取开销而没有均衡收益。相比之下 random/skewed 的串行基线受访存不规则或负载不均拖累，并行后反而有更多可弥补的空间。

4. 公开矩阵与云端隐藏矩阵不同。你的方案面对未知行长度分布时可能有哪些优势和风险？

答：优势：按行划分 + `dynamic(64)` 不依赖任何具体矩阵名称或尺寸，对未知分布具有通用性，能自动适应长行集中或随机分布；每行由单一线程完成，正确性天然成立。风险：若隐藏矩阵存在极长行（例如单行 nnz 接近总 nnz），按行划分会退化为一个线程独占长行、其余线程空转，加速比接近 1；dynamic 在均匀矩阵上比 static 略多开销；此外本方案未按非零元再切分，无法让多线程分担同一长行。

### 实验总结

用自己的话总结本实验中最重要的一个认识、遇到的一个问题及解决过程。

答：本实验最重要的一个认识是“正确性、并行性、性能是三个不同的要求”：数据竞争和逻辑错误要分开看，`default(none)` 只是帮你显式声明数据属性，并不会自动消除竞争；性能上“线程越多越快”是错的，按 nnz 而非行数衡量的负载均衡、以及它与调度开销之间的权衡才是关键。我遇到的一个问题是 skewed 矩阵上 guided 调度竟和 static 一样严重不均衡——排查后发现 guided 的初始 chunk 较大、恰好覆盖了集中在前四分之一的长行，于是把调度换成 `dynamic(64)`，负载立刻均衡，耗时从约 0.55ms 降到约 0.19ms。这个过程让我真正理解了调度策略的分配粒度与负载分布之间的关系。
